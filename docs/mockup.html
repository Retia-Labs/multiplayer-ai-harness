Quorum Retia Labs

One laptop has the repo. Everyone builds anyway.

Quorum is a multiplayer AI coding IDE. You describe what you want, an agent does it, and anyone you read a code out to joins the same run — from their own laptop, without cloning anything. They watch it, talk in it, redirect it, and approve the risky bits. Nobody has to look at code unless they actually want to type.

Four things that are true of it

All four are built and covered by tests today

the run is not in your window

Close the laptop; it keeps going

The agent runs in its own process. Quit the app mid-task and reopen it — the work continued and the app reattaches. That is also why anyone else can join: there is something to join.

join with a code, not an account

No repo, no install, no login

Someone who has never seen the codebase can watch it being changed, ask questions, and approve a risky command. They are replayed everything from before they arrived.

approvals are facts, not pop-ups

Anyone in the room can unblock it

A risky command stops the run for everybody. Whoever is around answers, from a laptop or a phone. The answer is recorded against a person, and the agent cannot approve itself.

the log is hash-chained

Nobody can rewrite what happened

Every event commits to the one before it. Edit or drop anything earlier and every hash after it breaks. Being in the room lets you take part in a run — never forge its history.

The same room, different work

The YC request says: anywhere a team already crowds around one problem. These are the crowds that already exist.

Nothing below needs a new product. A run is a run: something long, something with steps, something that occasionally has to stop and ask a person. Only the tools the agent is given change.

on-call · incidents

The war room

Three engineers already crowd around one problem at 3am, in a Slack huddle, watching one person type. Now the agent reads logs and proposes the fix while everyone watches, and the person with production access approves the deploy — from their phone, without opening a laptop.

Same room. Different tools: logs, metrics, deploy instead of shell and write_file. The incident review writes itself, because the log already says who approved what and when.
support · escalations

The escalated ticket

An agent works one hard ticket end to end: reads the account, reproduces the problem, drafts the fix and the reply. Support watches, the engineer joins when it gets technical, and the refund needs someone with authority to approve it.

Same room. Different tools: the CRM, the account, the refund API. The approval gate is already the shape this needs.
deals · pricing

The deal desk

A rep, a solutions engineer and a finance approver already crowd around one contract. The agent assembles the quote, the security answers and the redlines; finance approves the discount inside the run rather than three days later in email.

Same room. Different tools: the CRM, the pricing sheet, the contract. Who approved which discount is exactly the question the chained log answers.
regulated work

The one that pays

Compliance, legal, clinical, financial operations. Teams that already accept process friction because they must be able to answer "who approved this, and when" a year later — and who cannot use a tool that only remembers a chat transcript.

Same room, same tools, same log — and here the tamper-evidence is not a nice detail, it is the reason they can buy it at all.

The honest ordering: coding is the one we know and the one with the volume, so it ships first. Incidents are the nearest neighbour — an on-call rotation is a crowd that already exists, unlike day-to-day coding where pairing is rare. The regulated cases are the ones where the log stops being a feature and becomes the reason to pay.
