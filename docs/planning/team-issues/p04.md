## What to build

Implement a complete account-to-project setup path: authenticate, create a private team, invite a named person, pair an execution host with local approval, and explicitly authorize one project. Treat identity and host authority as distinct from encryption access and billing.

Type: **AFK**. Suggested work lane: **Collaboration/encryption**. Parent user stories: 4, 5, 17, 45.

## Acceptance criteria

- [ ] An owner can create a team, issue an expiring invitation, accept it as another authenticated user, and remove membership; name-only login and caller-supplied roles cannot bypass authorization.
- [ ] Pairing requires local host consent and selecting an allowed workspace. A remote user cannot register arbitrary paths, claim another runtime, or escalate execution policy.
- [ ] Direct protocol/HTTP requests enforce account, team, project and host boundaries; outsider history access and foreign runtime routing fail with distinct errors.
- [ ] Team administration or a paid seat alone grants neither project decryption nor action-approval authority. UI communicates the pending encryption-enrollment state.

## Blocked by

None — can start immediately.
